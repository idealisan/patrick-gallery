# S3: 全量重建的链式分批执行

- **Epic**: [维护与自愈体系](../maintenance-self-healing.md) · WI-1 / §5.5 决策
- **优先级**: P0 · **估算**: 1d · **状态**: 待开工（依赖 S1 + S2）

## User Story

作为管理员，当我触发 force 全量重建时，系统应当**自动地、一批接一批**地处理
全部资产——队列里永远只有一个待跑批次，绝不一次性创建海量任务，也绝不允许
一个任务吃下全部数据。

## 决策依据（§5.5）

- 批次任务**链式创建**：当前批次完成 → 再创建下一批 → 直至游标耗尽
- 分批间隙用户新插入的数据自然走正常上传流程，不进入本次重建集合，影响可忽略
- 禁止实现：触发时一次性物化全部 item 的"伪全量"

## 验收标准

1. force 触发时只物化**第一批**；后续批次由完成回调链式派发
2. 每批之间有可观测的间隙（进度快照可见 batchesDone 递增）
3. 链式过程中用户可暂停（PUT queue paused）→ 停止派发下一批；恢复后从断点续
4. 游标推进期间新写入的资产不会被本轮重建包含（用起始快照 id 上界保证）
5. 服务重启时：未完成的链式任务丢弃并记录日志（幂等，可重新 force 触发）
6. 集成测试：200 个模拟资产、batchSize=50 → 恰好 4 批、顺序推进、暂停/恢复生效

## 实现要点

- 断点状态存内存 jobState 即可（重启放弃是明确行为）；如后续要持久化再议
- 起始 id 上界 = 触发时刻 `MAX(id)`（或快照集合），杜绝"追着新数据跑"
